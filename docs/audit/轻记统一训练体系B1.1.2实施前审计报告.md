## 二、`TrainingViewModel.save()` 完整调用链（真实路径）

文件：`app/src/main/java/com/qingji/app/ui/viewmodel/TrainingViewModel.kt`

```
save(onDone)
 ├─ savingGuard.compareAndSet(false,true)        // AtomicBoolean 入口 CAS（L476）
 ├─ _isSaving.value = true
 ├─ snapshot = _draft.value                       // 不可变快照（L484）
 ├─ snapshotRevision = snapshot.revision
 ├─ typed = exercises.map { TrainingItemMapper.resolveType(e.recordType, entity) }
 ├─ 门槛校验：strengthDrafts / nonStrength
 ├─ 构建 WorkoutSession（editing / backfill / normal 三分支）
 └─ viewModelScope.launch {
      try {
        ├─ repo.saveUnifiedSession(session, strengthItems+otherItems, cardioItems, weight)
        ├─ 版本化清理：current == null || current.revision == snapshotRevision → clear() 否则保留新草稿
        ├─ hasActual / ExerciseCalorieHint.message(...) → say(...)
        └─ onDone(true)                           // ★ 缺陷 1：在 try 内
      } catch (e: Exception) {
        ├─ say("保存失败...")
        └─ onDone(false)                          // ★ 缺陷 1/2：回调异常与取消都走到这里
      } finally {
        ├─ savingGuard.set(false)
        └─ _isSaving.value = false                // 锁释放正确
      }
    }
```

### 缺陷 P0-1：异常捕获范围过大，可产生"数据库成功、UI 失败"不一致

- `onDone(true)`、`say()`、草稿清理后的提示逻辑全部在 `try` 内。
- 若 `repo.saveUnifiedSession()` 已成功提交事务，而 `onDone(true)`（UI 关闭页面、导航回调）抛异常，
  异常会被 `catch (e: Exception)` 捕获，转而执行 `onDone(false)`。
- 结果：数据已落库，UI 却收到失败反馈，用户可能重试导致重复提交（虽然 CAS 会拒绝，但语义错误）。

### 缺陷 P0-2：`CancellationException` 被当作普通失败吞掉

- `kotlinx.coroutines.CancellationException` 是 `Exception` 子类，落在 `catch (e: Exception)` 内。
- 协程取消被降级为 `onDone(false)` + "保存失败"提示，违反结构化并发约定，且取消后锁虽释放但语义错误。

### 待证语义：`sessionUuid` / `editingUuid`

- 新建训练：`WorkoutDraft.sessionUuid = UUID.randomUUID()`，`editingUuid = ""`（L189）。
- 编辑历史：`editSession()` 中 `sessionUuid = session.uuid` 且 `editingUuid = session.uuid`（L306/L311）。
- T14 保留的新草稿沿用同一 `sessionUuid`。因此：
  - 新建场景第二次保存 → `sessionDao.insert`（REPLACE 同 uuid）应更新同一场，不产生重复；
  - 编辑场景第二次保存 → 仍更新原历史场，不覆盖其他场。
- **该语义目前只有代码推断，没有真实 Repository + Room 的两次保存测试证明**（本次补 T15/T16）。

## 三、`WorkoutDraftStore` 落盘链路

文件：`app/src/main/java/com/qingji/app/data/prefs/WorkoutDraftStore.kt`

- `load()`（L97）：从 `SharedPreferences[workout_draft][draft_json]` 读取，含 `revision` 字段回读（L133）。
- `save(draft)`（L138）：整包写 JSON，含 `revision`（L154）；`sp.edit().putString(...).apply()` 异步落盘。
- `clear()`（L174）：移除草稿键。
- **落盘异常风险**：`persist()` 先 `_draft.value = versioned` 再 `draftStore.save(versioned)`；
  `apply()` 本身不抛异常，但如果 `save()` 抛异常（如注入失败），内存已更新、磁盘未更新，
  revision 一致性被破坏。本次补 T20 验证并明确处理。

## 四、所有修改 `WorkoutDraft` 的入口（枚举，实测）

`_draft.value =` 赋值点仅 3 处：
- L455 `discard()` → clear + null（放弃）
- L597 保存成功且版本未变 → clear + null（正常清理）
- L636 `persist()` 内 → versioned（唯一内容修改入口）

`persist(...)` 调用点共 17 处，覆盖：
- 初始化/恢复（L196/L208/L214）、新增动作（L221/L257）、编辑载入（L304/L338）
- 时长覆盖（L272）、补记日期（L278）、删除动作（L420）、备注（L425）
- 力量组增删改/完成切换（L363/L372/L386/L406/L413）、暂停恢复（L450）

暂停恢复 `togglePause()`（L442）也走 `persist(next)`。
**结论：所有草稿内容修改均统一经过 `persist()`，revision 单调递增覆盖完整。**
唯一需加固的是"落盘失败时内存/磁盘一致性"（见上）。
