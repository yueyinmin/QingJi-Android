## 3. 刷新调用位置与调用链

**全部走 `WidgetRefresher`，无直接 `updateAppWidget`**：MainActivity.onCreate `refresh(ALL)`(`MainActivity.kt:48`)；QingJiRepository 中 saveWeight→WEIGHT(:169)、addFoodLog/moveMeal/replaceMeal/addWater→OVERVIEW(:820,835,847,883,899)、clearRecords/factoryReset→ALL(:1346,1415)；SettingsViewModel→ALL(:352,359)；AddWaterAction→`refreshNow(OVERVIEW)`(`WidgetActions.kt:67`)；系统周期刷新由 3 个 XML 的 1800000ms 触发。
调用链：`refresh()`→`scope.launch{mutex.withLock{queued+=targets}}`(:105-108)→`init` 泵 `queued.collectLatest`(:131-139)→`delay(250)`→快照清空→`refreshNowInternal`→`GlanceAppWidget.updateAll`(:122)。
**QUICK 目标无显式刷新调用点**（`WidgetTarget.QUICK` :45 仅定义，只在 ALL 时间接刷新）。

## 4. 刷新实现现状

无独立文件；`WidgetRefresher` 在 `WidgetActions.kt:76-144`。请求合并 250ms 属实（:134），`collectLatest` 语义为后沿去抖。定向 `enum WidgetTarget{QUICK,OVERVIEW,WEIGHT}`(:45)，`widgetOf` 映射(:97-101)，`ALL=entries.toSet()`(:88)。实际显式使用：WEIGHT(1)、OVERVIEW(5)。`updateAll` 逐组件 try/catch 吞异常(:120-125)。注意区分 AddWaterAction 600ms 防抖(:72) 与 Refresher 250ms 合并(:134) 是两套机制。

## 5. AddWaterAction 防抖与生命周期风险

`lastClickAt` 是 `ActionCallback` **实例字段**(`WidgetActions.kt:50`)，600ms 判断(:57-59)。Glance `actionRunCallback<AddWaterAction>()` 可能每次点击重建实例（**待验证：需 instrumentation 确认**），若重建则防抖失效、连点重复 +200ml。另：一次点击触发双重刷新（`QingJiRepository.addWater` 内 refresh(OVERVIEW) :883 + Action 内 refreshNow(OVERVIEW) :67，后者绕过合并）。字段无 `@Volatile`；写库异常静默吞(:62-66)。

## 10. 旧 Provider 兼容风险

**三要素必须逐字保留**：Receiver 类名(`AndroidManifest.xml:96,108,120` ↔ `WidgetReceivers.kt:20,25,30`)、Provider XML 资源名(Manifest :104,116,128)、`updatePeriodMillis`/`initialLayout`。改任一都会让桌面已存在组件变「未找到小组件」。可行升级：保留三要素，仅替换 `glanceAppWidget` 返回的新实例（**待验证**：Glance 是否支持旧 Receiver 名指向新 Widget）。`targetCellWidth/Height`(Android 12+)与 `minWidth/minHeight`(低版本兜底)必须同时保留。

## 11. 可复用 / 缺失 / 重复

- **可复用**：跨进程 `SettingsStore.observe().first()`；QingJiRepository 的 4 个 observe/latest；`ExerciseCompensation.remainingWithBonus`、`WeightUnit.formatWithSymbol`；现成 `DailyHealthSummaryEntity` 聚合；`WidgetRefresher` 队列骨架；`TARGET_*`/`EXTRA_TARGET` 路由常量。
- **缺失**：独立 WidgetRefresher 文件；专用 Widget 快照层（有现成 DailyHealthSummary 但未用）；QUICK 显式刷新点；预览与 Glance 共享规格；Widget 自动化测试。
- **重复/不一致**：3 套每日汇总表达（DailySummary / DailyHealthSummaryEntity / WidgetData）；饮水目标双源；剩余热量双公式；`qingji_target` 字面量两处(WidgetActions.kt:42,79)；宏量色双份；`MacroBar` 进度宽 `64.dp*progress` 与轨道 `fillMaxWidth` 不匹配(QingJiWidgets.kt:390,399,407)；一次喝水双重刷新；600ms/250ms 两套防抖。

## 12. 推荐最小改动路径

- **阶段 0（零风险搬家）**：把 `WidgetRefresher` 原样拆到独立文件，保留对象名/方法/枚举/常量字面值；**不动** Manifest 三 name、三个 XML 文件名与 updatePeriod、路由字符串、SettingsStore 键名。
- **阶段 1（统一口径，不改 UI）**：新增 `WidgetSnapshotRepository`/UseCase，复用现有 Repository + SettingsStore（饮水目标改设置优先）+ `remainingWithBonus`（剩余热量含补偿）+ 可选 DailyHealthRepository（运动/睡眠/容量）；`loadWidgetData` 改为委托，保留 lastGoodData 兜底；给 QUICK 明确刷新点。
- **阶段 2（修刷新与防抖）**：防抖状态改进程级/持久化；去掉双重刷新二选一；改后 instrumentation 确认 Glance 实例化行为。
- **阶段 3（预览对齐）**：抽共享 `WidgetSpec`（尺寸/文案/颜色/开关），预览与 Glance 共用常量，消除已列差异。
- **明确不动**：Receiver/Provider XML 身份、业务聚合 SQL、Destinations 路由与 MainActivity.readTarget 消费逻辑。
