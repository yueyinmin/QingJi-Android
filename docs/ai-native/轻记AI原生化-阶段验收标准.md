4. 构建结果：`compileDebugKotlin`、`testDebugUnitTest`、`assembleDebug`、`assembleRelease` 至少四项。

## 1. 阶段 B：AI 基础设施

### 功能验收

- [ ] 存在统一 `AiProvider` 抽象，业务代码不再直接依赖具体 `AiClient` 类型。
- [ ] 能力声明覆盖 CHAT / STREAMING / TOOL_CALLING / STREAMING_TOOL_CALLING / JSON_SCHEMA / IMAGE_INPUT / AUDIO_INPUT。
- [ ] 普通文本生成可用。
- [ ] SSE 文本流可用，逐字输出不断流。
- [ ] 非流式 Tool Calling 可用。
- [ ] 流式 Tool Call 参数可正确拼接，callId 对应正确。
- [ ] JSON Schema 严格输出可用；不支持时降级有日志且调用方可见。
- [ ] 保留 `IMAGE_INPUT` 能力声明与现有图片接口兼容；**不要求中餐识别/匹配/营养计算，语音不作为 B 阻塞项（R5）**。
- [ ] 连接测试可报告能力，不仅返回“成功/失败”。
- [ ] 请求可取消；取消后不再占用连接/额度。
- [ ] 错误模型覆盖工单 4.4 全部错误类型，UI 不显示笼统“请求失败”。
- [ ] 多服务商配置可增删改，默认模型可设置。
- [ ] **B 阶段基线安全（R7）**：API Key 安全复用、日志脱敏、上下文最小化、请求取消、网络失败降级全部具备；K/L 只做完整专项验收。

### 测试要求

- 网络层必须引入可注入 OkHttpClient 并使用 MockWebServer。
- 覆盖：普通响应、SSE 分片、工具调用分片、400 `response_format` 降级、401/429/5xx、超时、取消。
- 协议解析规则尽量抽成纯 Kotlin 单测，避免依赖 Robolectric。

### 通过条件

- 所有 B 节用例通过；`compileDebugKotlin` / `testDebugUnitTest` / `assembleDebug` / `assembleRelease` 通过。
- 明确区分“支持 SSE 文本流”和“支持流式工具调用”。

## 2. 阶段 C：Agent 与只读工具

### 功能验收

- [ ] `QingJiAgent` 可完成多轮工具调用。
- [ ] 单次任务 ≤4 轮模型交互；单轮 ≤5 工具；总 ≤10 工具，由代码强制。
- [ ] 工具调用并行/串行状态可追踪；单响应多个 tool_call 时按各自 `callId` 回传，A 的结果不会串到 B。
- [ ] 流式参数片段完整拼接后才执行；不完整片段不触发业务。
- [ ] 工具失败返回结构化错误（code/message/toolName/callId），按供应商协议回传模型。
- [ ] 工具参数经 JSON Schema 校验，错误参数不执行业务；模型输出不能覆盖只读白名单。
- [ ] 工具超时、失败、重复调用、任务取消、无限循环防护均可工作。
- [ ] `ContextBuilder` 按任务注入数据，不默认上传全库。
- [ ] 上下文有 Token 预算、数据范围、时间范围、来源标识、缺失标识。
- [ ] **数据来源五分类（R9）**：实际记录 / 本地计算 / AI 推断 / 数据不足 / 建议；AI 推断不得伪装成实际记录。
- [ ] 四个只读工具全部可用：`get_today_summary`、`get_daily_nutrition`、`get_training_history`、`get_training_plan`。
- [ ] AI 不能直接访问 DAO；工具只读白名单外方法不可调用。

### 测试要求

- 单工具、多工具、多轮、参数错误、超时、重复调用、循环防护、取消。
- 工具返回结果与业务页面一致（同一天首页/训练历史/计划页对比）。
- 任何工具测试不得写库。

### 通过条件

- 只读工具结果与现有页面一致；无写库副作用；无绕过 Repository。

## 3. 阶段 D：AI 会话页面

### 功能验收

- [ ] 统一 AI 管家入口可打开会话列表与当前会话。
- [ ] 支持文本、图片输入；语音入口按项目现状接入或明确标为后续。
- [ ] 支持流式文本、工具过程提示、工具执行状态。
- [ ] 支持中断生成、失败重试、会话切换。
- [ ] 页面退出后任务状态不丢失或可取消。
- [ ] 首页/饮食/训练/训练历史/训练计划/身体数据/统计页的上下文入口都进入同一会话系统。
- [ ] 视觉符合轻记主题，不像独立客服页面。

### 测试要求

- Compose UI 测试至少覆盖入口跳转、消息发送、中断、重试。
- 若 Robolectric UI 测试仍被 @Ignore，必须标注“未执行”，不得声称通过。

### 通过条件

- 所有入口统一；AI 失败时退出会话后原业务仍可用。

## 4. 阶段 E：提案与安全执行

### 功能验收

- [ ] 提案记录工单 7.1 全部字段。
- [ ] 提案状态机覆盖 PENDING_CONFIRMATION / EXECUTING / EXECUTED / REJECTED / STALE / FAILED / EXPIRED。
- [ ] 确认页展示原因、修改前、修改后、差异、影响、确认与拒绝。
- [ ] 训练计划/营养目标具备版本字段与 CAS 更新。
- [ ] 所有正式写入入口统一维护版本号。
- [ ] 幂等键防重复确认、网络重试、Agent 重复生成。
- [ ] **主库 `ai_proposal_execution` 是唯一权威执行状态（R2）**；AI 库只更新展示状态，启动时按 `idempotency_key` 对账。
- [ ] 主库事务只写正式数据 + EXECUTED/STALE；事务失败整体回滚，**在事务外**写 FAILED + 原因（R3）。
- [ ] `EXECUTING` 启动扫描可恢复：按幂等键判定已执行或重新入队/转 FAILED，不永久卡住。
- [ ] 恢复后版本不匹配或目标不存在的提案标记 STALE，禁止执行。

### 测试要求

- 正常确认、拒绝、版本冲突、重复确认、执行失败、成功但状态回写失败、崩溃恢复、`EXECUTING` 卡死恢复、过期、恢复后 STALE。
- 跨库一致性对账测试：AI 库展示状态与主库权威状态不一致时以主库为准。

### 通过条件

- 未通过 E，不得进入 F/G 的写入功能。

## 5. 阶段 F：AI 饮食助手

### 功能验收

- [ ] 图片/包装食品/多图/自然语言输入可用；语音可标后续。
- [ ] AI 输出菜品、食材、做法、份量、重量区间、置信度、不确定因素。
- [ ] `FoodMatchingEngine` 混合召回：标准名、别名、关键词、FTS（如实现）、食材、做法、规则排序。
- [ ] **通用别名是版本化只读食物数据，不放 AI 库；用户纠正存主库用户侧表；模型不改公共词库（R6）**。
- [ ] 支持至少工单举例的别名组：番茄炒蛋/西红柿炒鸡蛋、木须肉/木樨肉、青椒肉丝/尖椒肉丝、宫保鸡丁/宫爆鸡丁。
- [ ] Top20 → Top5 → 精排 → 无匹配兜底链路完整。
- [ ] 营养值由 `NutritionCalculator` / 本地规则计算，带 nutrition_source / is_estimated / confidence / matched_id 等语义。
- [ ] 确认卡片可替换食物、改重量、增删食物、改餐次、查看营养与估算标识。
- [ ] 确认前绝不写正式饮食记录。

### 测试要求

- 标准食物、别名、中餐菜品、组合菜、无匹配、估算、重量修改、营养重算、正式写入。
- 与首页今日记录营养口径一致。

### 通过条件

- 无匹配时明确返回；营养值不来自模型直接断言；确认链路无提前写库。

## 6. 阶段 G：AI 训练助手

### 功能验收

- [ ] 可读取当前计划、历史训练、动作重量/次数/组数、时长、频率、完成情况。
- [ ] 力量/有氧/HIIT 按原语义读取，不被统一成同一种结构。
- [ ] 支持自然语言训练反馈与历史对比。
- [ ] 训练量、表现、安排、恢复分析在数据充分时可用；不足时说明不确定性。
- [ ] 计划调整只生成提案，确认后才改正式计划，版本 +1。
- [ ] MET/热量继续调用现有计算逻辑。

### 测试要求

- 三类运动读取；历史分析；计划提案；版本冲突；确认执行；原有训练功能回归。

### 通过条件

- 不破坏统一运动体系；无 AI 专属运动模型；计划修改全部经提案。

## 7. 阶段 H：身体数据与综合健康分析

### 功能验收

- [ ] 体重、BMI、体脂率、围度等只用现有计算逻辑。
- [ ] 趋势分析结合饮食、运动、训练、目标、数据完整度。
- [ ] 体脂率缺可靠数据时标估算，不写正式身体数据。
- [ ] 日/周/月/阶段报告区分：实际记录、计算结果、AI 推断、数据缺失、建议。

### 测试要求

- BMI 与现有结果一致；缺数据不崩溃；报告字段齐全。

### 通过条件

- 模型不自行计算确定性指标；不写猜测数据。

## 8. 阶段 I：长期记忆

### 功能验收

- [ ] 记忆按工单 11.1 分类，有来源、创建时间、过期/失效、用户纠正入口。
- [ ] AI 猜测不得直接保存为用户事实。
- [ ] 按任务选择性注入，不把全部聊天作为记忆。
- [ ] **区分用户事实与 AI 推断；删除会话不等于删除长期记忆；删除长期记忆需用户显式操作（R10）**。
- [ ] 个人食物纠正不污染公共食物库。

### 测试要求

- 记忆创建/查询/修改/失效/过期清理；跨任务注入边界。

### 通过条件

- 用户可查看与纠正；无关任务不注入无关记忆。

## 9. 阶段 J：主动 AI

### 功能验收

- [ ] 本地规则先判断，事件触发，数据充分性检查后才可调用 AI。
- [ ] 去重、频率限制、静默时段、用户关闭、任务取消、网络失败降级齐全。
- [ ] 不每次打开 App 都无条件请求模型。

### 测试要求

### 通过条件

- 无打扰性调用；用户可完全关闭。

## 10. 阶段 K：数据安全与隐私

### 功能验收

- [ ] API Key 不进日志/备份/聊天/普通数据库。
- [ ] 每次请求明确数据范围与用途，优先摘要。
- [ ] 用户提供的数据删除与隐私清理入口可覆盖 AI 会话/记忆。
- [ ] 云端请求最小化与日志脱敏通过专项审计。

### 测试要求

- 数据删除、日志脱敏、Key 不导出、隐私控制。

### 通过条件

- Key 与用户隐私数据不出现在日志、聊天、备份或普通数据库。

## 11. 阶段 L：性能与稳定性（含备份恢复、异常恢复）

### 功能验收

- [ ] Token usage 记录 input/output/provider/model/time/task；无数据则留空。
- [ ] 上下文按任务加载，历史消息长度受控。
- [ ] AI 页面打开、会话列表、长对话滚动、图片等待、流式渲染不卡顿。
- [ ] 断网、超时、取消、切后台、进程回收、工具失败、版本冲突、重复确认、迁移失败均有降级。
- [ ] AI 库备份段可导出/恢复；老备份无 AI 段不误清；恢复顺序明确；版本不匹配提案 STALE；恢复出厂覆盖 AI 数据。

### 测试要求

- 性能记录（页面打开/滚动/查询耗时）；失败注入测试；旧备份/新备份/AI 段缺失/版本冲突/恢复后 STALE 测试。

### 通过条件

- AI 网络任务不阻塞主线程；失败不影响原业务。
