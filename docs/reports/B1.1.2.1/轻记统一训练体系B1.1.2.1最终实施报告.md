## 一、修复说明

### P0-1 条件清理同时校验身份与版本

| 项 | 修改前 | 修改后 |
|---|---|---|
| API | `clearIfRevision(expectedRevision)` 只比 revision | `clearIfMatches(expectedSessionUuid, expectedRevision)` 同时比 sessionUuid 与 revision |
| 锁 | `WorkoutDraftStore` 实例级 `draftLock` | companion 级 `DRAFT_LOCK`，进程内跨实例共享 |
| ViewModel | `current == null` 时调用无条件 `draftStore.clear()` | 所有分支统一用 `clearIfMatches(snapshot.sessionUuid, snapshotRevision)`，不再无条件 clear |
| 误删场景 | A/B 训练都 revision=1，A 保存完成会删 B | 身份不匹配即保留 B |

涉及文件：
- `app/src/main/java/com/qingji/app/data/prefs/WorkoutDraftStore.kt`
  - `companion object` 中新增 `private val DRAFT_LOCK = Any()`，注释说明生产中存在多实例写同一 SP 文件。
  - `save()` / `clear()` / `clearIfMatches()` 全部 `synchronized(DRAFT_LOCK)`。
  - `clearIfMatches()` 在锁内依次执行：读当前草稿 → 校验 sessionUuid → 校验 revision → 满足才 remove。
- `app/src/main/java/com/qingji/app/ui/viewmodel/TrainingViewModel.kt`
  - 保存成功后统一调用 `draftStore.clearIfMatches(snapshot.sessionUuid, snapshotRevision)`。
  - `cleared == true` 才清 `_draft`；`current == null` 分支不再无条件清理，仅保留内存已空的事实。
  - 版本变了提示“新修改仍保留”；身份变了提示“身份或版本已变化，草稿已保留”。

**多实例核查证据**：生产代码中 `TrainingRepository` 持有 `WorkoutDraftStore(context)`，
`QingJiRepository`（清草稿 / 恢复出厂）又 `new WorkoutDraftStore(context)`，
因此实例级锁确实不足，改为 companion 共享锁。SharedPreferences 为 MODE_PRIVATE，多进程不在本类保证范围。

### P1-1 备份恢复设置副作用

| 项 | 修改前 | 修改后 |
|---|---|---|
| 写入位置 | `restoreInto()` 在 Room 事务内直接 `SettingsStore.set(AI_ACTIVE_PROVIDER_ID, valid)` | `restoreInto()` 只返回 `RestoreSideEffects(aiActiveProviderId)`，`importJson()` 在 `db.withTransaction` 提交后应用 |
| 系统边界 | SettingsStore 是 DataStore，属于 Room 事务之外的存储系统 | 明确记录；事务回滚时设置不再被提前修改 |
| 失败语义 | 设置写失败会被外层 catch 转成整体恢复失败 | 设置写入与 Widget 刷新都 `runCatching`，已提交的 DB 恢复不再被误报失败 |

涉及文件：`app/src/main/java/com/qingji/app/data/backup/BackupManager.kt`
- 新增 `internal data class RestoreSideEffects(val aiActiveProviderId: Int? = null)`。
- `restoreInto()` 返回类型改为 `RestoreSideEffects`，v7 分支只记录 `pendingAiActiveProviderId`。
- `importJson()` 在事务提交后应用副作用。
- **不迁移设置存储到 Room**，不新增表，不改 schema/migration。
- 新增测试：`BackupRollbackB112Test.恢复落库只返回AI激活设置副作用不在Room事务内写DataStore`，
  验证事务内 DataStore 值不变、返回值正确、显式应用后更新。

**无法自动化验证的边界**：DataStore 写失败的真实磁盘异常难以稳定注入；当前通过 `runCatching` 从代码路径保证
不会误报整体失败，但没有构造真实 DataStore IO 故障的自动化用例。
