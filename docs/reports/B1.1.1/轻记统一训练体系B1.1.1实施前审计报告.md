## 三、保存并发与草稿一致性核查（P0 缺陷）

### 3.1 save() 无互斥

文件：`app/src/main/java/com/qingji/app/ui/viewmodel/TrainingViewModel.kt:461-572`

- `save()` 是普通函数，内部直接 `viewModelScope.launch { ... }`；
- 全类搜索无 `isSaving` / `saving` 字段（grep 无命中）；
- 连续调用两次 `save()` 会启动两个协程，各自 `repo.saveUnifiedSession()`；
- `saveUnifiedSession()` 内虽用 `db.withTransaction`，但事务只保证单批次原子性，两个协程串行执行时，第二次会用同样 `session.uuid` 再次 insert + delete + upsert。**会话 UUID 相同不会新增第二行，但账本 upsert 与日记 upsert 依赖 sourceId 幂等，实际是否完全无副作用缺少断言**（缺陷 D-03：需 T12 证明）。

### 3.2 草稿快照与清理存在竞态

- `save()` 在第 462 行取 `val d = _draft.value`，该 `d` 是不可变 data class，本身构成快照；
- 但协程执行 `repo.saveUnifiedSession(...)` 期间，用户若继续编辑，`persist()` 会更新 `_draft.value` 和磁盘；
- 保存完成后第 558 行无条件 `draftStore.clear()` + 第 559 行 `_draft.value = null`，**会把保存期间的新修改一并清掉**（缺陷 D-04：需 T14 证明）；
- 数据库异常时，`saveUnifiedSession()` 抛错，`draftStore.clear()` 不会执行（因在 suspend 返回后），草稿理论上保留；但没有 try/catch，异常直接冲垮协程，`onDone(true)` 不回调，也无用户反馈（缺陷 D-05：需 T11 证明）；
- `WorkoutDraft` 无 revision/version 字段，无法比较"当前草稿版本 vs 本次保存版本"（缺陷 D-04 的实现前提）。

### 3.3 进程恢复

`WorkoutDraftStore.save()` 用 `SharedPreferences.edit().apply()` 同步落内存、异步落磁盘；`load()` 从 `KEY_DRAFT` 读取。`persist()` 每次改动调用 `save()`。ViewModel 构造时会 `load()`。已有测试仅通过重建 ViewModel 验证，未做真实进程/SharedPreferences 磁盘级恢复验证（缺陷 D-06）。
